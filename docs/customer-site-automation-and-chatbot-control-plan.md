# EXTAY 고객별 모바일 가이드 자동화 및 챗봇 운영 설계안

작성일: 2026-09-11  
상태: 기획·설계 문서. 이 문서 작성 시점에는 관리자 페이지와 챗봇 ON/OFF 기능을 구현하거나 배포하지 않았다.

## 1. 확정된 사업 원칙

EXTAY는 고객마다 독립된 모바일 가이드 사이트를 제공한다. 여러 숙소를 하나의 공용 사이트 안에서 경로만 나누는 방식은 사용하지 않는다.

고객별 기본 구성은 다음과 같다.

- 고객 전용 모바일 가이드 사이트와 주소
- 고객 소유 GitHub 저장소
- 고객 소유 Vercel 프로젝트
- 고객 소유 OpenAI 계정·프로젝트·API 키·결제
- 고객 숙소에 맞춘 정보, 이미지, 디자인 설정과 챗봇 지식
- 고객별 챗봇 사용량·호출 한도·캐시의 논리적 분리

고객은 비개발자일 수 있으며 GitHub, Vercel, OpenAI 개발자 화면을 지속해서 다루지 않는 것을 기본 전제로 한다. EXTAY 제공자는 고객 100명 이상이 되어도 반복적인 수동 운영대행을 하지 않는 구조를 목표로 한다.

## 2. 해결해야 할 운영 문제

고객별 저장소와 배포 프로젝트를 단순 복제하면 다음 작업이 고객 수만큼 반복된다.

- 새 고객 저장소와 Vercel 프로젝트 생성
- 숙소 데이터와 이미지 교체
- API 키와 환경변수 등록
- 도메인 연결과 초기 배포
- 챗봇 정책·보안·성능 개선의 반복 반영
- 장애 시 챗봇 중단 및 복구
- 고객의 숙소 정보 변경 요청 반영

따라서 고객별 독립 사이트 원칙을 유지하면서 생성·설정·업데이트·중단 작업만 자동화해야 한다.

## 3. 권장 구조: 고객별 사이트 자동 생성 시스템

EXTAY의 현재 사이트를 마스터 템플릿으로 정리하고, 고객별 차이는 코드가 아니라 설정과 콘텐츠로 분리한다.

```text
고객별 모바일 가이드
├─ 공통 EXTAY 엔진
│  ├─ 화면과 내비게이션
│  ├─ 챗봇 요청·응답 처리
│  ├─ 출처·지도 링크 표시
│  ├─ 호출 제한과 오류 처리
│  └─ 관리자 기능
│
└─ 고객별 설정
   ├─ 숙소 기본 정보와 이용 규칙
   ├─ 체크인·체크아웃·교통·시설 정보
   ├─ 이미지와 브랜드 설정
   ├─ 호스트 연락 경로
   ├─ OpenAI 연결 정보
   └─ 챗봇 사용 여부와 사용 한도
```

### 신규 고객 생성 흐름

1. 고객 또는 제작자가 온보딩 양식에 숙소 정보와 자료를 입력한다.
2. 자동 생성 시스템이 마스터 템플릿에서 고객 전용 GitHub 저장소를 만든다.
3. 고객 전용 설정과 이미지가 저장소에 반영된다.
4. 고객 Vercel 계정에 프로젝트를 만들고 저장소를 연결한다.
5. 고객 OpenAI API 키와 필요한 서버 환경변수를 Vercel에 등록한다.
6. 자동 검증을 통과하면 고객 전용 주소에 배포한다.
7. 배포 결과와 관리자 페이지 주소를 고객에게 전달한다.

계정의 이메일 확인, 결제수단 등록, 2차 인증과 최초 권한 승인은 고객이 한 번 수행해야 한다. 이후의 사이트 생성과 배포는 자동화 대상으로 삼는다.

## 4. 고객용 관리자 페이지

고객에게 GitHub나 Vercel 사용법을 가르치는 대신, 숙소 운영에 필요한 항목만 보이는 관리자 페이지를 제공한다.

초기 관리자 기능 범위는 다음과 같다.

- 챗봇 ON/OFF
- 숙소 기본 정보 수정
- 체크인·체크아웃 정보 수정
- 와이파이·주차·쓰레기·세탁·시설 안내 수정
- 사진과 링크 교체
- 자주 묻는 질문 추가·수정
- 챗봇 호출 수와 사용 한도 확인
- 변경 내용 미리보기와 게시

관리자 페이지에서는 API 키 원문, GitHub 설정, Vercel 배포 설정을 노출하지 않는다. 고객마다 별도 관리자 계정 또는 일회용 로그인 링크를 사용하며, 모든 고객이 공유하는 하나의 관리자 비밀번호는 사용하지 않는다.

## 5. 챗봇 ON/OFF 기능 명세

### 목적

OpenAI API 장애, 비용 이상, 악성 반복 호출, 챗봇 답변 품질 문제, 숙소 운영자의 요청이 있을 때 해당 고객 사이트의 챗봇을 즉시 중단할 수 있어야 한다.

### 관리자 동작

- 관리자는 현재 상태가 `사용 중`인지 `사용 중지`인지 확인할 수 있다.
- ON/OFF 스위치를 변경할 때 저장 여부를 명확히 보여준다.
- OFF 사유를 선택하거나 짧게 기록할 수 있다.
- 변경 시각과 변경 주체를 기록한다.
- OFF에서 ON으로 복구할 때 상태 조회와 시험 질문을 먼저 확인할 수 있다.

권장 상태 데이터는 다음과 같다.

```json
{
  "siteId": "extay-mansion-haebangchon",
  "chatbotEnabled": false,
  "disabledReason": "OpenAI API 장애",
  "updatedAt": "2026-09-11T10:00:00+09:00",
  "updatedBy": "property-admin"
}
```

### OFF일 때 고객 화면

챗봇 관련 요소를 단순 비활성 버튼으로 남기지 않고 전부 표시하지 않는다.

- 상단 챗봇 버튼 숨김
- 홈의 AI 컨시어지 입력 영역 숨김
- 플로팅 챗봇 버튼과 인사 말풍선 숨김
- 검색 결과의 AI 컨시어지 항목 숨김
- 열려 있던 챗봇 패널 닫기
- 챗봇 자동 인사와 추천 질문 실행 중지

숙소의 일반 가이드, 검색, 체크인, 와이파이, 교통, 시설, 연락처 기능은 그대로 제공한다.

### OFF일 때 서버 동작

화면 숨김만으로는 직접 API 호출을 막을 수 없다. 서버의 `/api/chat`도 같은 상태값을 확인한 뒤 OpenAI를 호출하기 전에 요청을 중단해야 한다.

- 챗봇이 OFF이면 OpenAI API를 호출하지 않는다.
- 직접 URL이나 자동 스크립트로 `/api/chat`을 호출해도 차단한다.
- 응답은 일관된 `CHAT_DISABLED` 상태 코드와 메시지를 사용한다.
- 상태 저장소를 읽지 못하는 장애가 발생하면 비용 보호를 위해 기본적으로 챗봇을 숨기고 API 호출을 중단한다.
- 관리자 상태 조회와 고객 화면 상태 조회는 캐시 때문에 오래 지연되지 않도록 구성한다.

### ON일 때 동작

- 고객 화면에서 챗봇 진입 요소를 표시한다.
- 숙소 매뉴얼 질문은 숙소 지식을 우선 사용한다.
- 일반 공개 정보는 필요한 경우에만 웹 검색한다.
- 출처 링크와 정확한 주소의 네이버지도·Google Maps 링크를 표시한다.
- 고객별 호출 한도와 검색 한도를 적용한다.

## 6. 상태 저장 위치

챗봇 ON/OFF 상태는 브라우저 로컬 저장소나 서버 함수 메모리에 저장하면 안 된다. 다른 기기와 다른 서버 인스턴스에 즉시 공유되는 영속 저장소를 사용해야 한다.

고객별 완전 분리를 우선하면 고객 Vercel 프로젝트에 연결된 Redis 또는 전용 설정 저장소를 사용한다. 관리 편의성을 우선하면 EXTAY가 관리하는 공용 저장소를 사용하되 모든 키를 `siteId`로 분리하고 고객 간 데이터 접근을 서버에서 차단한다.

예시 키는 다음과 같다.

```text
site:extay-mansion-haebangchon:chatbot:enabled
site:extay-mansion-haebangchon:chatbot:reason
site:extay-mansion-haebangchon:chatbot:updated-at
```

## 7. 반복 질문·API 응답·사용량 저장

모든 고객 대화를 영구 저장하지 않고 목적별로 분리한다.

| 데이터 | 권장 저장 | 보관 원칙 |
|---|---|---|
| 숙소 공식 정보 | 고객별 설정 파일 또는 DB | 버전 관리 후 영구 보관 |
| 반복 숙소 질문 답변 | 고객별 캐시 | 지식 버전이 바뀌면 무효화 |
| 공개 실시간 정보 답변 | 짧은 캐시 | 정보 성격에 따라 수분~수시간 |
| 호출 제한 카운터 | Redis | 분·시간·일 단위 자동 만료 |
| 모델·토큰·검색 사용량 | 고객별 집계 | 일·월 단위 집계 |
| 개선용 질문 로그 | 익명화 저장소 | 개인정보 제거 후 제한 보관 |

개인정보, 예약번호, 연락처와 특정 투숙객 맥락이 포함된 대화는 공용 답변 캐시에 저장하지 않는다.

## 8. API 비용 및 악성 호출 보호

고객별 사이트가 계속 공개되므로 챗봇 ON/OFF 외에도 다음 보호가 필요하다.

- 같은 요청의 연속 제출과 중복 클릭 차단
- IP와 익명 방문자 ID를 조합한 단기 호출 제한
- 사이트별 일일·월간 AI 호출 한도
- 웹 검색 호출의 별도 한도
- 숙소 반복 질문의 정적 답변 또는 캐시 우선 처리
- 요청 길이와 대화 이력 길이 제한
- 일일 비용 임계값 초과 시 자동 OFF 또는 매뉴얼 답변 전용 모드
- Vercel 방화벽과 봇 탐지 적용
- OpenAI 사용량·오류율·검색 사용량 기록

챗봇이 화면에 보이는 것만으로 API 비용이 발생하지는 않는다. 질문 제출 시에만 요청하도록 유지하고, OFF 상태에서는 화면과 서버를 모두 차단한다.

## 9. 공통 기능 업데이트 방식

고객 사이트 100개를 직접 수정하지 않도록 공통 엔진과 고객 설정을 분리한다.

권장 방식은 공통 엔진을 버전이 있는 패키지 또는 동기화 가능한 템플릿으로 관리하고, 새 버전이 검증되면 자동화가 각 고객 저장소에 업데이트를 반영하는 것이다.

자동 업데이트는 다음 조건을 지켜야 한다.

- 고객별 숙소 설정과 이미지를 덮어쓰지 않는다.
- 자동 테스트를 통과한 버전만 배포한다.
- 일부 고객부터 순차 배포한 뒤 전체 고객으로 확장한다.
- 실패한 고객 프로젝트만 별도로 재시도한다.
- 배포 버전과 실패 이유를 한 화면에서 확인할 수 있게 한다.
- 긴급 문제가 생기면 이전 공통 엔진 버전으로 되돌릴 수 있게 한다.

## 11. 완료 기준

다음 조건이 모두 충족되어야 고객별 사이트 자동화가 완료된 것으로 본다.

- 고객별 GitHub·Vercel·도메인·OpenAI 비용이 독립되어 있다.
- 새 고객 사이트를 표준 입력만으로 생성할 수 있다.
- 고객이 개발 도구 없이 숙소 정보를 수정할 수 있다.
- 관리자가 챗봇을 OFF하면 모든 고객 화면에서 챗봇이 사라진다.
- OFF 상태에서 `/api/chat`을 직접 호출해도 OpenAI 요청이 발생하지 않는다.
- 저장소 장애 시에도 비용이 발생하는 방향으로 자동 복구되지 않는다.
- 공통 기능을 고객별 콘텐츠 손상 없이 일괄 업데이트할 수 있다.
- 배포·호출·오류·비용 상태를 고객 사이트별로 확인할 수 있다.

## 12. 이번 작업의 범위

이번 작업은 위 운영 구조와 관리자 챗봇 ON/OFF 기능을 문서로 정의하는 데 한정한다. 관리자 페이지, 상태 저장소, API 차단, 고객 화면 숨김, Vercel 배포는 아직 구현하지 않았다.
